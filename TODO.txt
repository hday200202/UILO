UILO TODO & Roadmap
===================

## Active -- Next Up (DAW foundations)

Immediate priorities, in order. UILO's end goal is a DAW, and the timeline needs
a small, coherent primitive set to draw grids, clips, automation and waveforms.
See "DAW FOUNDATIONS & THE ZEN DAW" at the bottom of this file for the design.

- [ ] 1. Remove uilo::Canvas and uilo::Waveform          <-- the next thing
      - Canvas was an immediate-mode experiment that fought the retained tree.
      - Waveform is app-specific; it belongs in the application, not the library.
      - Both are replaced by uilo::Shape below.

- [ ] 2. uilo::Shape -- retained custom geometry (vertex array)
      - Declarative geometry AS AN ELEMENT, not immediate-mode draw calls.
      - Two layers: a friendly polyline/shape (points + stroke/fill + topology)
        over a raw mesh/vertex buffer for the power case.
      - Render-only (no hit-testing); interaction lives on the containers around it.
      - A parametric "repeat" rule for instanced geometry (grid lines, ticks,
        meter segments): describe spacing/step/extent/colour, UILO owns and
        batches the geometry (GPU instancing stays an internal optimisation). A
        thin `grid` convenience adds tiers (bar/beat/subdivision) and LOD culling
        (drop a tier under ~6px on-screen spacing).
      - Also needed: a content-space positioned container -- children placed by
        explicit (x, y) in content coords, following scroll/zoom -- so clips,
        piano roll and automation are composed elements, not one giant blob.

- [~] 3. Context Menu -- NATIVE DONE, web pending
      Root-held as specified: UILO holds one ContextMenu, built on first use, and
      an element declares items with Modifier::setContextMenu -- a fixed list, or
      a builder run on each right-click for a menu that follows state. The
      deepest element under the cursor with items wins and consumes the click.
      Done: submenus to any depth, per-item icons, separators, disabled items,
      keyboard navigation (up/down skipping separators and disabled rows, right
      and left to enter and leave a submenu, enter to pick, escape to back out),
      edge flipping on both axes, and a pooled row set that is only ever
      relabelled so the structure survives.
      Verified by tools/probe.sh ctxmenu -- 26 assertions against a real window.
      - [ ] Web: Translator has no case for it yet. The rows are ordinary
            Buttons in a Column so the geometry translates as-is, but the
            browser's own menu has to be suppressed, the contextmenu event wired
            to the same dispatch, and a menu whose row pool GROWS mid-session
            needs the overlay re-translated -- syncFloating only translates a
            backdrop it has not seen, and re-uses it by pointer thereafter.
      - [x] examples/contextmenu.cpp -- a DAW-shaped timeline: lanes with a
            builder menu, clips with a list menu of their own (so the deepest
            element wins), a transport bar, and the page background, for four
            distinct menus. A status line shows which action ran.

- [ ] 4. Animation (detail under Features & Infrastructure below)

Only what is left to do. Finished work is documented in README.md and in the
headers, not here.

## Widgets not started

- [ ] Tabs / Tab Bar
      Closeable tabs, active-tab highlight, and overflow -- either scroll the
      strip or spill into a menu. Page switching already exists (setPage), so a
      tab bar is a control for it rather than new machinery.

- [~] Context Menu (right-click)   [see "Active -- Next Up", item 3 for state]
      include/elements/widgets/ContextMenu.{hpp,cpp}, plus the item type in
      include/utils/ContextMenuItem.hpp -- kept free of every element type
      because Modifier stores it and Modifier is included by everything.

- [ ] Modal Dialog
      addPopupBackdrop already gives the full-window scrim that swallows input.
      What is missing is the dialog itself: a titled card, button presets
      (OK/Cancel, Yes/No), and a custom button row.

- [ ] Toast Notifications
      Corner-anchored, auto-dismissed after a timeout, several stacked at once.

- [ ] Progress Bar
      Horizontal and vertical, determinate and indeterminate, optional label.

- [ ] Checkbox
      Including the partial look for tri-state, with a label.

- [ ] Switch / Toggle
      A checkbox that slides. Wants the animation system below, or a hand-rolled
      lerp until it exists.

- [ ] Tooltip
      Shown after a hover delay and auto-flipped so it does not run off the
      window edge. Needs a per-element hover timer, which nothing keeps today.

- [ ] Breadcrumb Navigation
      The clickable path trail along the top of a view -- "Home / Projects /
      UILO", where each segment jumps to that level and the middle collapses to
      an ellipsis when the row is too narrow to fit. The concrete use here would
      be a path bar above the FileBrowser. It is a Row of Buttons plus that
      overflow rule, so decide first whether it earns being a widget at all.


## Features

- [~] Palette
      Done: central definitions in Defaults.hpp, runtime switching, per-UILO
      override via UILO::setTheme (which is what gives Wt sessions their own
      look), and every widget following roles with nothing named at the call
      site. A Palette is now reachable only through a Theme -- there is no
      UILO::setPalette any more.
      - [ ] Serialization / deserialization
      - Literal-only on purpose, not a gap: transparent-by-default container
        fills and outlines (a role would paint every container), Image tint (a
        role would tint photographs), Waveform channel colours, and the
        translucent overlays whose alpha carries the effect -- DatePicker's scrim
        and range fill, Textbox's selection. Roles cannot express alpha over an
        unknown background.

- [~] Theme
      Rebuilt 2026-08-23, twice. A Theme is the palette plus one prototype per
      Modifier and *Options type, all declared in include/Defaults.hpp -- the
      single file that carries the library's look. A UILO owns its theme
      (ui.getTheme() / ui.setTheme()); there is no global, and no way to install
      a palette without going through a Theme.
      - Applied when an element BINDS to its UILO, not when it is constructed,
        which is what lets a tree be built before the UILO exists (the idiomatic
        UILO ui(renderer, buildMainPage())) and what makes setTheme() restyle a
        running app with nothing rebuilt.
      - Every themeable field is a Themed<T>: a value plus one bit saying whether
        the call site set it. That bit is the whole system -- a theme fills gaps
        and never overrides a setting, and inheriting leaves the bit clear so a
        later theme change still reaches the field.
      - Named roles carry shape the way the palette carries colour, and the
        h1/h2/h3/body/caption/panel/card/primaryButton/ghostButton helpers in
        Factory.hpp are one line each over them. That is the "reusable style
        bundles" item this entry used to carry.
      - [ ] Not every field is themeable yet. Converted: the optionals (padding,
            rounding, char size, stroke), every colour role, every thickness,
            Modifier's width/height/align/visible, and Text's weight and
            alignment. Still plain, so a theme cannot set them: literal Colors,
            item heights, and most per-widget numbers. Same Themed<T> treatment
            when one earns it.
      - [x] Roles cascade over the type's default (fixed 2026-08-23). They used
            to be a snapshot: edit() seeded a new role by copying the default,
            so changing a shared value afterwards reached every plain element
            and silently skipped every one that named a role -- the theme
            example's Square/Rounded/Pill buttons did nothing to anything
            role-styled. A role now holds only what it overrides, and cascade()
            composes it over the default at read time.
      - [x] inheritRounding pinned instead of deferring (fixed 2026-08-23).
            Converting the fields to Themed<T> turned `m_rounding = own` into
            `m_rounding.set(own)`, which marked the field explicit even when
            `own` was empty -- so every inner part a composite widget built
            through it stopped following the theme. The dropdown's popup was the
            visible half; its header only appeared to work because it is a
            Button picking up the base ButtonOptions radius. Now only a real
            value counts as a setting.
      - [ ] Composite widgets build their inner elements in their constructor,
            before the theme is applied. Colour is fine (it resolves at draw),
            but a themed SIZE on an inner part is read before it arrives. Either
            rebuild inner parts in applyTheme or read those options lazily.
      - [ ] Loading a theme from a file, so a look can be edited without a
            rebuild. The prototypes are plain setters, so this is a
            serialization problem shared with the Palette entry above.
      - [ ] More themed properties as they earn it -- scroll speed, spacing
            scale, hover/pressed tints.

- [ ] Animation System
      Shape to aim for:

          element->animate(from, to, how, duration);

      where `from` and `to` are Modifiers or Options and `how` is the KIND of
      transition -- fade, slide, scale, and so on. The kind is a separate axis
      from the easing curve: easing shapes the timing (linear, ease-in,
      ease-out), while the kind decides what actually moves. Two things can
      travel between the same pair of endpoints over the same duration and still
      read completely differently.
      Kinds worth having: fade, slide (from an edge, so it needs a direction),
      scale/pop, and cross-fade for a swap. Plus start/end callbacks.
      - [ ] Decide what `how` means when `from` and `to` are full Modifiers,
            because the two overlap: if the endpoints differ in position that is
            already a slide, and if they differ in alpha that is already a fade.
            Either a kind is a PRESET that derives the endpoints itself
            (animate(Fade::In, 200ms) with no from/to written out), or it is the
            PATH taken between endpoints that were given -- an arc rather than a
            straight line, or move-then-fade rather than both at once. Probably
            both, with the preset form as the short spelling.
      - [ ] Fade has nowhere to write to. There is no opacity on Modifier or on
            Element; alpha only exists inside each Options' colours, so fading an
            arbitrary element means walking every colour it has, or adding an
            element-level opacity that render() multiplies through. The second is
            the smaller change and the only one that works for a whole subtree.
      - [ ] Decide how an element knows when to animate -- the reason this has
            not started. A manual animate() call, a callback, or an event
            binding. Note that hover already has enter/exit transitions to hang
            one off, and examples/text-editor.cpp fades a resizer by hand from an
            onUpdateEnd handler, which is what this system should replace.

- [ ] Drag and Drop
      Draggable elements, drop targets, and visual feedback during the drag.
      Wants a payload bucket on the mouse so a drag can carry arbitrary data and
      the drop target can ask for it at the end.

- [ ] Keyboard Navigation
      Tab order, a focus indicator, arrow keys within a container.

- [ ] Virtual Scrolling
      Render only the visible rows, so a 10k-item list stays cheap.

- [x] Native File Dialog Abstraction  (include/utils/FileDialog.hpp)
      openFileDialog / openFilesDialog / saveFileDialog / selectFolderDialog,
      plus fileDialogsAvailable(). Type filters, a start path and a default name
      go in through FileDialogOptions; each returns std::optional or a vector, so
      cancelling is a value rather than an error. No third-party code: NSOpenPanel
      on macOS (platform/MacFileDialog.mm), IFileDialog on Windows, and
      zenity/kdialog/qarma on Linux, behind a header that names none of them.
      - [ ] Blocking only. While a dialog is up the caller's loop is not running,
            so the window behind it stops redrawing -- which is what the platform
            dialogs do anyway, but an async form returning a pollable handle
            would let an app keep animating.
      - [ ] Linux is untested here; there is no Linux machine in this
            environment. The zenity and kdialog command lines are written from
            their documented flags, not from a run.
      - macOS needs the call to come from a UILO app: the panels attach to the
        NSApplication the Renderer's window creates. A console program that never
        opened a window gets an immediate cancel.

- [ ] OS-level drag and drop INTO the window -- dropping a file onto the app.
      System clipboard integration is already done.


## Known gaps

- Vendored versions
      - [x] bx / bimg / bgfx are pinned to commit SHAs in build.sh. They used to
            be cloned at HEAD while SDL3 was pinned, so a clone made on a
            different day got a different bgfx -- and today's shaderc has dropped
            the GLSL "120" profile CMakeLists.txt asks for, failing every shader
            with "Unknown profile: 120" on a fresh checkout.
      - [ ] Bumping those three is a deliberate step: check
            _UILO_SHADER_PROFILES in CMakeLists.txt still names profiles the new
            shaderc has, since bgfx removes them without notice.

- Terminal
      - [ ] Windows. Pty.cpp's Windows branch fails cleanly with "needs
            ConPTY", so the widget reports it could not start a shell rather
            than half-working.
      - [ ] Mouse reporting (CSI ?1000h and friends), so a mouse-driven TUI
            never sees clicks. Whoever adds it must gate drag-to-select on
            reporting being OFF, or selection will keep stealing the drag.
      - [ ] No reflow on resize. The grid is resized and the shell is
            SIGWINCHed, but wrapped lines are not re-wrapped -- a cell grid has
            already thrown away the text that would be needed.
      - Not fixable: the browser cannot host this. A page cannot fork a process,
        and proxying one would hand every visitor a shell on the host. Pty is
        stubbed in wt/HeadlessBackend.cpp so the WT build links, and Translator
        renders the screen text as a monospace block.

- Input
      - [ ] Touch / pointer support
      - [ ] IME, for international text entry

- Rendering
      - [ ] High DPI
      - [ ] Sub-pixel positioning and text antialiasing quality

- Layout
      - [ ] Untested edge cases: very small containers, deeply nested trees,

## Tools

- [x] uilo-new -- project generator (tools/uilo-new/)
      One target, two front-ends over the same scaffolding code: `uilo-new <path>`
      creates a project and exits, `uilo-new` with no path opens a UILO window
      with the same form. Writes bin/, ext/ and src/ plus a CMakeLists.txt and a
      build.sh; nothing is downloaded at generation time.
      The generated build.sh checks for git, cmake, python3, a compiler and (on
      Linux) SDL3's X11/Wayland packages and offers to install what is missing,
      clones UILO into ext/UILO at a pinned ref, has it provision its own
      dependencies, then builds into bin/.
      - Windows is Git Bash only, deliberately, like UILO's own build. The
        README and the CMake error messages that pointed at a build.ps1 which
        never existed now say so.
      - [ ] Only two templates (minimal, panels). A web/Wt starter would need
            UILO_WT wiring in the generated CMakeLists.
      - [ ] No `--list-templates`, and no way to add templates without a rebuild.


## Testing & docs

Two probes are the test suite. Both drive elements directly with no UILO bound,
so they need no window and no GPU:

      tools/probe.sh layout     22 cases, dumps every child's resolved bounds.
                                --baseline saves the golden output, --check
                                diffs against it.
      tools/probe.sh pointer    23 assertions, self-checking, exits non-zero on
                                failure. Covers occlusion: who ends up hovered,
                                whose handlers fire, what a floating child
                                shields.
      tools/probe.sh ctxmenu    26 assertions. Needs a window and a GPU, unlike
                                the other two: a menu measures its own labels
                                and flips against the window edges.
      tools/gen_docs.py --check doc-comment coverage
      tools/check_readme.py     compiles every code block in README.md
      examples/render_bench     rendering throughput

- [ ] Neither probe covers a widget yet, only containers and dispatch. Add cases
      as widgets land.
- [ ] gen_docs.py --check reports 24 gaps, all in include/wt: Translator's
      reconcilePages and translatePageInto, and UiloWt's serverArgs, argPointers
      and both UILO::runWeb overloads.
- [ ] Example apps still missing: todo list, settings panel, dashboard.


================================================================================
PHASE 2 -- fold Row and Column onto one axis-generic implementation
================================================================================
Phase 1 is done: update() and render() are split into named phase functions in
both classes, so the two line up function-for-function and the duplicated
resizer block inside each file is gone. What is left is the duplication BETWEEN
Row.cpp and Column.cpp.

Worth doing because 63 of 67 accessor names are already identical between
RowOptions and ColumnOptions -- the only genuine difference is the zoom axis
(getZoomableX vs getZoomableY). A template over the Options type therefore works
by duck typing: no common base class, no virtuals, no change to the public API
or to the Wt bridge.

Shape to aim for: a detail-namespace axis policy in containers/AxisLayout.hpp
holding main/cross accessors (main, cross, mainDim, isEnd, isMid), then one
templated implementation of each phase -- updateScrollable, updateFlow,
layoutResizers, renderSubdivisions, renderChildPass -- taking <Axis, Options>.
Row.cpp and Column.cpp shrink to their policy plus m_zoomX / m_zoomY.

Two real divergences, to decide BEFORE merging. These are behaviour, not
cosmetics:

  1. Resizer cross-axis sizing. Column::layoutResizers computes a span, clamps
     the Modifier width into it, and honours Align::Right / Align::CenterX to
     place the handle within that span. Row::layoutResizers does none of it and
     stretches the handle across the whole cross span -- Column was improved at
     some point and Row never was.
     Recommendation: unify upward so Row gains it, which CHANGES Row's resizer
     bounds.

  2. Zero-delta scroll guard. Row::checkScroll(float) returns false on a zero
     delta, so a purely vertical wheel bubbles to the parent. Column has no such
     guard and consumes the event.
     Recommendation: unify upward so Column gains the guard.

Verify with `tools/probe.sh layout --check`: the output must be byte-identical
EXCEPT for the cases that exercise divergence 1. Read case 12 ("column flow:
resizers, cross-axis align") carefully when accepting new golden output. Then
`tools/probe.sh pointer`, which must stay at 23/23.
