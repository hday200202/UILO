UILO TODO & Roadmap
===================

## Active -- Next Up (DAW foundations)

Immediate priorities, in order. UILO's end goal is a DAW, and the timeline needs
a small, coherent primitive set to draw grids, clips, automation and waveforms.
See "DAW FOUNDATIONS & THE ZEN DAW" at the bottom of this file for the design.

- [ ] 1. Remove uilo::Canvas and uilo::Waveform          <-- the next thing
      - Canvas was an immediate-mode experiment that fought the retained tree.
      - Waveform is app-specific; it belongs in the application, not the library.
      - Both are replaced by uilo::Shape below.

- [ ] 2. uilo::Shape -- retained custom geometry (vertex array)
      - Declarative geometry AS AN ELEMENT, not immediate-mode draw calls.
      - Two layers: a friendly polyline/shape (points + stroke/fill + topology)
        over a raw mesh/vertex buffer for the power case.
      - Render-only (no hit-testing); interaction lives on the containers around it.
      - A parametric "repeat" rule for instanced geometry (grid lines, ticks,
        meter segments): describe spacing/step/extent/colour, UILO owns and
        batches the geometry (GPU instancing stays an internal optimisation). A
        thin `grid` convenience adds tiers (bar/beat/subdivision) and LOD culling
        (drop a tier under ~6px on-screen spacing).
      - Also needed: a content-space positioned container -- children placed by
        explicit (x, y) in content coords, following scroll/zoom -- so clips,
        piano roll and automation are composed elements, not one giant blob.

- [ ] 3. Context Menu (detail under Medium-Priority Widgets below)
      - Root-held: UILO keeps one empty context-menu element at the very root of
        the UI; right-clicking an element defines what that menu contains.

- [ ] 4. Animation (detail under Features & Infrastructure below)

Only what is left to do. Finished work is documented in README.md and in the
headers, not here.

## Widgets not started

- [ ] Tabs / Tab Bar
      Closeable tabs, active-tab highlight, and overflow -- either scroll the
      strip or spill into a menu. Page switching already exists (setPage), so a
      tab bar is a control for it rather than new machinery.

- [ ] Context Menu (right-click)   [see "Active -- Next Up", item 3]
      - Root-held design: UILO holds a single empty context-menu element at the
        very root of the UI (a surface above the page). Right-clicking an element
        populates that shared menu with the items that element defines, then
        shows it at the cursor.
      - Submenu support
      - Keyboard navigation
      - Icon support per item

- [ ] Modal Dialog
      addPopupBackdrop already gives the full-window scrim that swallows input.
      What is missing is the dialog itself: a titled card, button presets
      (OK/Cancel, Yes/No), and a custom button row.

- [ ] Toast Notifications
      Corner-anchored, auto-dismissed after a timeout, several stacked at once.

- [ ] Progress Bar
      Horizontal and vertical, determinate and indeterminate, optional label.

- [ ] Checkbox
      Including the partial look for tri-state, with a label.

- [ ] Switch / Toggle
      A checkbox that slides. Wants the animation system below, or a hand-rolled
      lerp until it exists.

- [ ] Tooltip
      Shown after a hover delay and auto-flipped so it does not run off the
      window edge. Needs a per-element hover timer, which nothing keeps today.

- [ ] Breadcrumb Navigation
      The clickable path trail along the top of a view -- "Home / Projects /
      UILO", where each segment jumps to that level and the middle collapses to
      an ellipsis when the row is too narrow to fit. The concrete use here would
      be a path bar above the FileBrowser. It is a Row of Buttons plus that
      overflow rule, so decide first whether it earns being a widget at all.


## Features

- [~] Palette
      Done: central definitions, runtime switching, per-UILO override (which is
      what gives Wt sessions their own look), and every widget following roles
      with nothing named at the call site.
      - [ ] Serialization / deserialization
      - Literal-only on purpose, not a gap: transparent-by-default container
        fills and outlines (a role would paint every container), Image tint (a
        role would tint photographs), Waveform channel colours, and the
        translucent overlays whose alpha carries the effect -- DatePicker's scrim
        and range fill, Textbox's selection. Roles cannot express alpha over an
        unknown background.

- [~] Theme
      Done: app-wide palette, rounding, outer padding, char size, font and icon
      stroke width; cascading element -> theme -> type default, so a theme only
      fills in what was left alone; composite widgets that keep following the
      theme after construction (inheritRounding). Deliberately NOT outline -- a
      border on everything reads as noise.
      - [ ] Font and char size still resolve once into widget label options, the
            way rounding used to. Only matters for a theme swapped at runtime;
            the same inherit* treatment fixes it.
      - [ ] Reusable style bundles: a named set of Options applied to many
            elements, which is the piece Theme deliberately does not cover.
      - [ ] More themed properties as they earn it -- scroll speed, spacing
            scale, hover/pressed tints.

- [ ] Animation System
      Lerp between two Modifiers, or two Options, over a duration, with easing
      (linear, ease-in, ease-out) and start/end callbacks.
      The open question, and the reason this has not started: how does an element
      know when to animate? A manual .animate(from, to, duration), a callback, or
      an event binding.

- [ ] Drag and Drop
      Draggable elements, drop targets, and visual feedback during the drag.
      Wants a payload bucket on the mouse so a drag can carry arbitrary data and
      the drop target can ask for it at the end.

- [ ] Keyboard Navigation
      Tab order, a focus indicator, arrow keys within a container.

- [ ] Virtual Scrolling
      Render only the visible rows, so a 10k-item list stays cheap.

- [ ] Native File Dialog Abstraction
      One interface over the OS open/save dialogs on macOS, Linux and Windows,
      with type filters, blocking or async, returning the chosen paths.

- [ ] OS-level drag and drop INTO the window -- dropping a file onto the app.
      System clipboard integration is already done.


## Known gaps

- Terminal
      - [ ] Windows. Pty.cpp's Windows branch fails cleanly with "needs
            ConPTY", so the widget reports it could not start a shell rather
            than half-working.
      - [ ] Mouse reporting (CSI ?1000h and friends), so a mouse-driven TUI
            never sees clicks. Whoever adds it must gate drag-to-select on
            reporting being OFF, or selection will keep stealing the drag.
      - [ ] No reflow on resize. The grid is resized and the shell is
            SIGWINCHed, but wrapped lines are not re-wrapped -- a cell grid has
            already thrown away the text that would be needed.
      - Not fixable: the browser cannot host this. A page cannot fork a process,
        and proxying one would hand every visitor a shell on the host. Pty is
        stubbed in wt/HeadlessBackend.cpp so the WT build links, and Translator
        renders the screen text as a monospace block.

- Input
      - [ ] Touch / pointer support
      - [ ] IME, for international text entry

- Rendering
      - [ ] High DPI
      - [ ] Sub-pixel positioning and text antialiasing quality

- Layout
      - [ ] Untested edge cases: very small containers, deeply nested trees,
            rapid add/remove cycles

- Memory & performance
      - [ ] Reduce allocations, cache layout calculations, cut draw calls


## Testing & docs

Two probes are the test suite. Both drive elements directly with no UILO bound,
so they need no window and no GPU:

      tools/probe.sh layout     22 cases, dumps every child's resolved bounds.
                                --baseline saves the golden output, --check
                                diffs against it.
      tools/probe.sh pointer    23 assertions, self-checking, exits non-zero on
                                failure. Covers occlusion: who ends up hovered,
                                whose handlers fire, what a floating child
                                shields.
      tools/gen_docs.py --check doc-comment coverage
      tools/check_readme.py     compiles every code block in README.md
      examples/render_bench     rendering throughput

- [ ] Neither probe covers a widget yet, only containers and dispatch. Add cases
      as widgets land.
- [ ] gen_docs.py --check reports 24 gaps, all in include/wt: Translator's
      reconcilePages and translatePageInto, and UiloWt's serverArgs, argPointers
      and both UILO::runWeb overloads.
- [ ] Example apps still missing: todo list, settings panel, dashboard.


================================================================================
PHASE 2 -- fold Row and Column onto one axis-generic implementation
================================================================================
Phase 1 is done: update() and render() are split into named phase functions in
both classes, so the two line up function-for-function and the duplicated
resizer block inside each file is gone. What is left is the duplication BETWEEN
Row.cpp and Column.cpp.

Worth doing because 63 of 67 accessor names are already identical between
RowOptions and ColumnOptions -- the only genuine difference is the zoom axis
(getZoomableX vs getZoomableY). A template over the Options type therefore works
by duck typing: no common base class, no virtuals, no change to the public API
or to the Wt bridge.

Shape to aim for: a detail-namespace axis policy in containers/AxisLayout.hpp
holding main/cross accessors (main, cross, mainDim, isEnd, isMid), then one
templated implementation of each phase -- updateScrollable, updateFlow,
layoutResizers, renderSubdivisions, renderChildPass -- taking <Axis, Options>.
Row.cpp and Column.cpp shrink to their policy plus m_zoomX / m_zoomY.

Two real divergences, to decide BEFORE merging. These are behaviour, not
cosmetics:

  1. Resizer cross-axis sizing. Column::layoutResizers computes a span, clamps
     the Modifier width into it, and honours Align::Right / Align::CenterX to
     place the handle within that span. Row::layoutResizers does none of it and
     stretches the handle across the whole cross span -- Column was improved at
     some point and Row never was.
     Recommendation: unify upward so Row gains it, which CHANGES Row's resizer
     bounds.

  2. Zero-delta scroll guard. Row::checkScroll(float) returns false on a zero
     delta, so a purely vertical wheel bubbles to the parent. Column has no such
     guard and consumes the event.
     Recommendation: unify upward so Column gains the guard.

Verify with `tools/probe.sh layout --check`: the output must be byte-identical
EXCEPT for the cases that exercise divergence 1. Read case 12 ("column flow:
resizers, cross-axis align") carefully when accepting new golden output. Then
`tools/probe.sh pointer`, which must stay at 23/23.
